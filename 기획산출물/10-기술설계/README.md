# 10-기술설계 — 무엇을 주고받고 어떻게 배포하나

새싹프렌즈 1팀 · 3차 프로젝트 · **수빈** 작성 / **병윤** 구현 · 2026-09-01

> 기술기획을 **두 관점**으로 나눠 담았습니다.

| 관점 | 무엇을 다루나 |
|---|---|
| 🅰️ **비즈니스 로직** | 서비스의 **핵심 시나리오**를 소프트웨어의 **기능과 성능**으로 표현. 이야기로 공유하기 위해 **시퀀스 다이어그램의 증강 형태**로 정리 |
| 🅱️ **딜리버리 로직** | 사용자의 **화면에 도달**하기 위한 기술적 방법. 사용 기술 스택에 따른 **FE–BE 구조와 배포 전략** |

---

## 🅰️ 비즈니스 로직

| 문서 | 내용 |
|---|---|
| [**증강 시퀀스 다이어그램**](%EC%A6%9D%EA%B0%95-%EC%8B%9C%ED%80%80%EC%8A%A4-%EB%8B%A4%EC%9D%B4%EC%96%B4%EA%B7%B8%EB%9E%A8.md) | 시퀀스 **7개**(SRS §3의 4개 증강 + 신규 3개). 화살표마다 **성능 상한 · 예외 분기 · 규제 게이트 · 이벤트 적재 · 멱등 키** 병기 |
| [**API 명세**](API-%EB%AA%85%EC%84%B8.md) | 엔드포인트 **39개**(부모 18 · 아이 10 · 외부 2 · 배치 9). 위 시퀀스의 화살표에서 그대로 뽑았습니다 |

**왜 API 명세가 여기 있나** — 스택과 무관하게 성립하는 **계약 수준**이고, 각 엔드포인트가 담는 것이 *"무엇을 주고받고 얼마나 빨라야 하는가"* 이기 때문입니다. **인증 구현·프레임워크·스키마 타입은 다루지 않습니다**(그건 🅱️와 병윤 님 재량).

## 🅱️ 딜리버리 로직

| 문서 | 내용 |
|---|---|
| [**시스템 아키텍처 · 배포 설계**](%EC%8B%9C%EC%8A%A4%ED%85%9C-%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98-%EB%B0%B0%ED%8F%AC%EC%84%A4%EA%B3%84.md) | **아키텍처**(신뢰 경계 4겹 · 계층 · 어댑터 · AI 두 평면) + **배포·환경**(환경 3종 · 배포 관문 6개 · 게이트 승격 · 롤백) |

**둘을 한 문서로 묶은 이유** — 배포 전략이 아키텍처 결정에서 곧바로 파생됩니다. 예를 들어 *「모의 ↔ 운영을 빌드 타임에 분리한다」* 는 배포 결정인데, 그 근거는 **발행사를 어댑터로 끊은 아키텍처 결정**입니다.

---

## 🔑 만든 순서 — 이유가 있습니다

```
① 증강 시퀀스  →  ③ API 명세  →  ②④ 아키텍처 · 배포
```

**시퀀스를 먼저 그리면 거기 나온 화살표가 그대로 API 목록이 됩니다.** API를 먼저 설계하면 **시나리오에 없는 엔드포인트**를 만들게 됩니다.

> 실제로 API 명세를 쓰면서 엔드포인트가 **36 → 39**로 늘었는데, 새로 만든 게 아니라 **시퀀스에 있던 화살표를 놓쳤던 것**이었습니다.

## 🤖 AI는 세 평면으로 갈라져 있습니다

정본은 [`SRS v1.0` §2.5.1](../00-%EC%82%AC%EC%96%91/SRS_%ED%95%80%ED%94%84%EB%A0%8C%EC%A6%88_v1_0.md)이고, 여기서는 **이 세 문서가 그 결정을 어디서 지키는지**만 적습니다.

| 평면 | 아동 데이터 | 이 산출물에서 |
|---|:-:|---|
| **D. 개발** | ❌ | 제품 런타임이 아니므로 **세 문서 어디에도 나오지 않습니다** |
| **A. 콘텐츠 저작** *(오프라인)* | ❌ | 아키텍처 §1에 **제품 경로 밖**으로 그렸습니다. 배치 잡도 엔드포인트도 만들지 않습니다 |
| **R. 제품 런타임** | ✅ | **`GET /parent/forest/summary` 한 곳**(`FR-042`) — 시퀀스 **S-7** · API 명세 **§1-6** |

🔴 **가드레일 6개 중 하나라도 못 지키면 `FR-042`를 끄고 템플릿 문장으로 되돌립니다.** 엔드포인트를 분리해 둔 이유가 이것입니다 — **끄는 일이 엔드포인트 하나를 내리는 일**이 됩니다.

## ⬜ 병윤 님이 정할 것

| 어디 | 무엇 |
|---|---|
| 시퀀스 §10 | **미확정 4건** — 미션 사진 보관 · 이자 지급 주체 · 주말 트리거 · 환불·파기 순서 |
| API 명세 §6 | 위 4건이 걸리는 **갈림길 3곳**. 나머지 엔드포인트는 **확정**이고, 정해지는 대로 §6만 갈아끼우면 됩니다 |
| API 명세 §8 | 인증 구현 · 에러 코드 · 페이지네이션 · 어댑터 인터페이스 |
| 아키텍처 §8-2 | 🔴 **벤더가 아니라 구성입니다** — 스키마 · IaC · 파이프라인 · SW 캐시 전략 · 관측 제품 · **LLM 페이로드 화이트리스트** |

📎 **호스팅·DB·CI·AI 벤더는 이미 정해졌습니다** — [`SRS v1.0` §2.5](../00-%EC%82%AC%EC%96%91/SRS_%ED%95%80%ED%94%84%EB%A0%8C%EC%A6%88_v1_0.md)가 정본이고, 아키텍처 §8-1에 그 위에 걸리는 조건을 정리해 뒀습니다.

🔴 **가장 먼저 닫아야 할 것은 시퀀스 §10-1(미션 사진 보관)** 입니다. **스토리지와 스키마를 바꾸므로** 뒤에 정하면 엔드포인트 시그니처까지 다시 써야 합니다.

## 📌 물러설 수 없는 것

구현 방식은 자유지만, 이 항목들은 **규제와 제품 결정에서 역산된 계약**입니다.

**API** *(명세 §8)* — 스코프 2종·403 강제 · 규제 게이트는 HTTP 상태로 거부 · 별이 움직이는 쓰기는 전부 멱등 · ⭐ 판정 스냅샷 고정 · 금지 컬럼 부재 · 주차 귀속은 `client_ts` · 🤖 **LLM 호출은 1곳 · 서버 경유 · 페이로드 화이트리스트**

**아키텍처** *(아키텍처 §8)* — 오리진 2개 분리 · 결제 원본 미보관 · 별 원장 append-only + 일일 대사 · 모의↔운영 빌드 타임 분리 · 제3자 오리진 요청 0건 · 🤖 **아이에게 가는 생성 텍스트 0건**
