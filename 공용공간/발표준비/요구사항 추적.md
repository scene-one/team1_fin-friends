# 요구사항 추적 — 기획서에서 코드까지

발표덱에 넣을 「추적 관계」 파트 초안입니다. 숫자는 전부 실제 산출물에서 가져왔습니다.
**일반 청중 기준**으로 썼습니다 — 내부 문서 번호와 코드 용어는 쓰지 않습니다.

**이 장이 답하는 것** — *"기획서를 썼다"* 와 *"그게 코드에 있다"* 는 다른 말입니다. 그 사이를 **우리가 무엇을 정해서** 이었는지가 이 파트의 주제입니다.

---

## 넣는 위치 — 두 장을 구현 앞에 붙입니다

| | 슬라이드 | 위치 |
|:-:|---|---|
| **A** | 사슬 한 장 — 무엇이 무엇을 낳았나 | 구현 파트 **맨 앞** |
| **C** | 한 문장이 여섯 번 구체화된다 — 별 이야기 | **A 바로 뒤** |
| | *(기존 구현 네 장)* | |
| **B** | 빠뜨린 게 없다는 건 어떻게 아나 | **백업** |
| **D** | 기능 · 성능 · 상태 · 예외가 어디서 붙나 | **백업** |

**A → C → 구현 4장** 순서가 *"이렇게 정했고 → 이게 코드까지 갔고 → 그 결과가 이겁니다"* 로 읽힙니다.
C에서 다룬 **별 이야기가 구현 세 번째 장에서 화면으로 다시 나오므로**, 청중은 앞에서 들은 것을 뒤에서 눈으로 확인하게 됩니다.

> 🔴 **B를 본편에서 뺀 이유** — 내용이 「자동 생성 · 자동 역산 · 자동 배정」으로 이어져서 **「도구가 다 해줬다」로 읽힙니다.** 정작 우리가 판단한 것(무엇을 타협하지 않을지, 무엇을 빼고 왜 뺐는지)이 가려집니다. 물어보면 그때 꺼냅니다.

---

## A. 사슬 한 장 — 무엇이 무엇을 낳았나

> **한 줄로 정하고, 잴 수 있게 만들고, 쪼개서 할 일로 냈습니다**

```
기획서  ──▶  명세서  ──▶  할 일 목록  ──▶  깃허브 이슈  ──▶  코드
```

| 단계 | 답하는 질문 | **이 단계에서 우리가 더한 것** | 규모 |
|---|---|---|:-:|
| **기획서** | 무엇을 왜 만드나 | 기능 목록과 **타협하지 않을 기준** | 기능 15가지 |
| **명세서** | **얼마나** 만족해야 하나 · **어떻게 확인**하나 | 항목마다 **확인 방법**과 **담당자** | 기능 17 + 성능·안전 18 = **35개** |
| **할 일 목록** | **누가 어떤 순서로** 만드나 | 먼저 할 것 · 난이도 · 몇 주차 | **68개** |
| **깃허브 이슈** | 지금 **어디까지** 왔나 | 조건별로 걸러 볼 수 있는 작업 카드 | **68개** |
| **코드** | 실제로 **도는가** | 화면 · 서버 · 데이터베이스 | — |

🔴 **단계마다 한 가지씩만 더합니다.** 기획서는 「왜」, 명세서는 「얼마나·어떻게 잴까」, 할 일 목록은 「순서」, 이슈는 「지금 어디」. **한 단계에서 두 가지를 하면** 다음 단계가 무엇을 받았는지 알 수 없게 됩니다.

**발표 대본**

이걸 어떻게 관리했는지 두 장으로 보여드리겠습니다. 기획서에서 무엇을 왜 만드는지 정하고, 명세서에서 그걸 얼마나 만족해야 하는지와 어떻게 확인할지를 붙였습니다. 항목이 기능 열일곱 개, 성능과 안전 쪽이 열여덟 개 해서 서른다섯 개입니다. 그걸 개발 단위로 쪼개서 할 일 예순여덟 개를 만들고, 그대로 깃허브 이슈 예순여덟 개로 올렸습니다. 저희가 정한 규칙은 하나입니다. 각 단계에서 한 가지씩만 더한다. 한 단계에서 두 가지를 하면 다음 단계가 무엇을 받았는지 알 수 없어지기 때문입니다.

## C. 한 문장이 여섯 번 구체화된다 — 별 이야기

> **기획서의 한 줄이 코드가 될 때까지, 매 단계에서 무엇이 더 구체적이 되는가**

| 단계 | 그 단계에서 이 문장은 |
|---|---|
| **기획서** | 아이가 모은 **별이 어긋나는 일은 0%.** 여기는 타협하지 않는다 |
| **명세서 — 기능** | 별을 주는 경우가 **여덟 가지**다. 쓰면 줄고, 초기화는 없고, **현금으로 바꾸는 길이 코드에 아예 없어야** 한다 |
| **명세서 — 확인 방법** | 경우별로 시험하고, **같은 요청을 두 번 보내 보고**, 장부를 대조하고, **현금 전환 코드가 없는지 자동으로 검사**한다 |
| **명세서 — 지도** | 이 요구사항은 **별 장부 담당**에 살고, 부품은 **장부 엔진 · 경우 분배기 · 중복 차단기**이고, **아이 홈 화면**에 나타난다 |
| **할 일 · 이슈** | 「별 장부 만들기」 · 난이도 **상** · **2주차** · ⚠️ **이게 밀리면 열한 개가 같이 밀린다** |
| **코드** | **잔액을 저장하지 않는다** — 장부 합이 곧 잔액이다. 중복은 코드가 아니라 **데이터베이스가 거부**한다 |

🔴 **두 번째 칸이 이 장의 핵심입니다.** 요구사항을 적을 때 **어떻게 확인할지를 같이 적지 않으면**, 나중에 「했다」고 말할 근거가 없습니다. 저희는 **35개 전부에 확인 방법을 붙였습니다.**

> *"0%로 하자"* 는 누구나 쓸 수 있습니다. **「같은 요청을 두 번 보내 본다」까지 적어야** 그게 검사가 됩니다.

**발표 대본**

하나만 끝까지 따라가 보겠습니다. 기획서에 「아이가 모은 별이 어긋나는 일은 0퍼센트, 여기는 타협하지 않는다」라고 한 줄이 있습니다. 아이가 모은 걸 잃는 경험이라 「조금은 괜찮다」를 안 두기로 한 겁니다. 이 한 줄이 여섯 번 구체화됩니다. 명세서에서 별을 주는 경우가 여덟 가지로 나뉘고, 현금으로 바꾸는 길이 코드에 아예 없어야 한다는 조건이 붙습니다. 그다음이 제일 중요한데, 그걸 어떻게 확인할지를 같이 적었습니다. 같은 요청을 두 번 보내 보고, 현금 전환 코드가 없는지 자동으로 검사한다. 0퍼센트로 하자는 누구나 쓸 수 있습니다. 두 번 보내 본다까지 적어야 그게 검사가 됩니다. 그리고 이게 할 일 하나가 되는데, 난이도 상에 2주차이고, 이게 밀리면 열한 개가 같이 밀린다고 적혀 있습니다. 마지막으로 실제 코드에서는 잔액을 아예 저장하지 않습니다. 장부에 쌓인 것의 합이 잔액이고, 중복은 코드가 판단하지 않고 데이터베이스가 거부합니다. 이 별 이야기는 잠시 뒤 화면으로 다시 보여드리겠습니다.

## B. 빠뜨린 게 없다는 건 어떻게 아나 *(백업)*

> **양쪽에서 셉니다**

| 방향 | 세는 것 | 결과 |
|---|---|:-:|
| 요구사항 → 할 일 | **담당 작업이 없는 요구사항** | 0개 |
| 할 일 → 요구사항 | **근거 요구사항이 없는 작업** | 0개 |

한쪽만 보면 **늘어난 것을 못 잡습니다.** 요구사항 쪽만 보면 아무도 시키지 않은 기능이 슬쩍 들어와도 모릅니다.

### 넣지 않은 것도 이유를 남겼습니다

| 뺀 것 | 왜 |
|---|---|
| 다른 앱의 기록 가져오기 | 이번 범위 밖으로 확정 |
| 문자 대체 발송 | **아직 못 정한 것**에 걸림 — 외부 발송 업체가 정해지기 전까지 만들지 않음 |
| 위치 기반 알림 | **없애기로 한 기능** — 계획에 없음 |
| **AI 기능** | **요구사항 35개 중 AI가 필요한 항목이 0개**였기 때문 |

> 이 표가 B의 본체입니다. **무엇을 넣었나보다 무엇을 왜 뺐나가 판단을 보여줍니다.**

### 그 위에 도구를 얹었습니다

할 일 문서는 원본 파일 하나에서 만들어지고, 「이게 밀리면 뭐가 밀리나」와 주차 배정은 자동으로 계산됩니다. 손으로 적으면 예순여덟 개 중 몇 개는 반드시 어긋나기 때문입니다.
**다만 무엇을 타협하지 않을지, 무엇을 뺄지는 도구가 정해 주지 않습니다.**

## D. 기능 · 성능 · 상태 · 예외가 어디서 붙나 *(백업)*

> **작업 카드의 칸 네 개가 각각 하나씩 담당합니다**

이슈 본문은 자유롭게 쓰는 게 아니라 **정해진 서식**입니다. 그래서 무엇이 빠졌는지 눈으로 셀 수 있습니다.

| 축 | 어느 칸에 | 예 |
|---|---|---|
| **기능** | 실행 계획 | *여덟 가지 경우에 별 주기* |
| **상태** | 실행 계획 — **상태가 어떻게 바뀌는지** | *완료 → 대기 → 승인 / 거절* |
| **성능 · 안전** | 지켜야 할 조건 | *어긋남 0% · 별 반영 0.8초 안 · 별은 모으기만* |
| **예외** | 완료 조건의 **실패 경우** | *현금으로 바꾸는 코드가 들어오면 → **빌드가 실패한다*** |
| **끝났다는 판정** | 완료 판정 | *같은 요청 두 번 보내도 중복 0건임을 증명했는가* |
| **일정 영향** | 선행 · 후행 | *이게 끝나야 시작되는 것 11개* |

### 상태와 예외를 왜 따로 적는가

**미션 승인**이 좋은 예입니다.

- **상태** — 완료 → **대기** → 승인 / **거절**. 네 가지를 다 적지 않으면 「거절」이 만들 때 사라집니다.
- **예외** — 그래서 완료 조건에 *"거절이 **안 한 것과 다르게 보이는가**"* 를 따로 겁니다.
- **이유** — 거절이 안 한 것과 같아 보이면 **아이 화면이 거짓말**을 합니다. 아이는 했는데 안 한 것으로 보입니다.

🔴 **저희에게 예외는 「오류 처리」가 아니라 「사용자가 겪는 나쁜 경우」입니다.** 그래서 기능 옆이 아니라 **완료 조건 안에** 넣었습니다 — 통과 여부를 재야 하기 때문입니다.

## 예상 질문과 답

**Q. AI는 어디에 쓰셨나요?**
제품에는 안 썼습니다. **요구사항 35개 중 AI가 필요한 항목이 0개**였기 때문입니다. 자리를 찾다가 못 찾은 게 아니라 **부르는 데가 없었습니다.** 월간 요약 문장 하나에만 쓰기로 하고 자리를 비워 뒀는데, 그게 없어도 숫자와 전월 대비 변화는 그대로 보입니다.

**Q. 이슈를 68개나 손으로 만드셨나요?**
아니요. 할 일 문서와 이슈를 원본 파일 하나에서 만들었습니다. 손으로 만들면 예순여덟 개 중 몇 개는 반드시 어긋납니다. **다만 무엇을 타협하지 않을지, 무엇을 뺄지는 저희가 정했습니다.**

**Q. 요구사항이 바뀌면 어떻게 하나요?**
원본을 고치고 문서를 다시 만듭니다. 할 일 문서를 직접 고치지 말라고 문서 첫머리에 적어 뒀습니다 — 「이게 밀리면 뭐가 밀리나」가 자동 계산이라 손으로 고치면 어긋납니다.

**Q. 문서대로 정확히 만들어졌나요?**
아니요. **달라진 곳이 있고 그것도 기록해 뒀습니다.** 개발하면서 문서와 달라진 지점마다 번호를 붙여 따로 장부에 남겼습니다 — 무엇이 왜 달라졌는지, 되돌릴지 문서를 고칠지까지 적혀 있습니다. 예를 들어 부모와 아이 화면을 서로 다른 주소로 나누려던 것은 하나의 앱이라 못 나눴고, 대신 세 겹으로 막으면서 그 대가를 장부에 적었습니다.

## 발표 전 확인할 것 *(우리끼리 볼 것)*

- ⬜ **번호 체계가 두 벌입니다.** 개발 중에 기준 문서를 새 명세서로 갈아탄 흔적이 남아 있어서, 할 일 문서와 코드 주석이 서로 다른 번호 체계를 가리킵니다. **청중에게는 번호를 아예 말하지 않고**, 물으면 그때 설명하는 편이 안전합니다
- ⬜ **이슈가 있는 저장소와 코드가 있는 저장소가 다릅니다.** 화면에 띄우신다면 어느 쪽을 열지 미리 정해 두세요
- ⬜ **자동 검사는 계획보다 적게 걸려 있습니다.** 지금 빌드에 물려 있는 건 일부입니다 — *"검사를 다 걸었다"* 고는 말하지 않는 게 좋습니다
- ⬜ A와 C 두 장이면 **약 55~65초**입니다. C의 대본이 A보다 깁니다
- ⬜ C에서 별 이야기를 먼저 하므로, **구현 세 번째 장에서 같은 이야기가 반복되지 않게** 그 장 대본을 *"아까 그 별 장부입니다"* 로 짧게 받는 편이 낫습니다
