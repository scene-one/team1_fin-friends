# 요구사항 추적 — 기획서에서 코드까지

발표덱에 넣을 「추적 관계」 파트 초안입니다. 숫자는 전부 실제 산출물에서 가져왔습니다.
**일반 청중 기준**으로 썼습니다 — 내부 문서 번호와 코드 용어는 쓰지 않습니다.

**이 장이 답하는 것** — *"기획서를 썼다"* 와 *"그게 코드에 있다"* 는 다른 말입니다. 둘을 잇는 사슬이 실제로 있는지, 그리고 **끊긴 데가 없다는 것을 어떻게 증명하는지**가 이 파트의 주제입니다.

---

## 넣는 위치 — 네 장을 다 넣지 않기를 권합니다

구현 네 장의 앞뒤를 **추적 이야기로 감싸는** 형태가 가장 짧고 강합니다.

| | 슬라이드 | 위치 |
|:-:|---|---|
| **A** | 사슬 한 장 — 무엇이 무엇을 낳았나 | 구현 파트 **맨 앞** |
| | *(기존 구현 네 장)* | |
| **B** | 사슬이 끊기지 않았다는 증거 | 구현 파트 **맨 뒤** |
| **C** | 하나를 끝까지 따라가기 — 별 이야기 | **백업** (질문 나오면) |
| **D** | 기능 · 성능 · 상태 · 예외가 어디서 붙나 | **백업** (질문 나오면) |

> 만드는 과정 이야기를 네 장 연속으로 두면 제품 이야기의 흐름이 끊깁니다. **A와 B만 본편에 두고 C·D는 뒤에 숨겨** 두었다가 *"어떻게 관리했냐"* 는 질문이 나올 때 꺼내는 편이 낫습니다.

---

## A. 사슬 한 장 — 무엇이 무엇을 낳았나

> **한 줄로 정하고, 잴 수 있게 만들고, 쪼개서 할 일로 냈습니다**

```
기획서  ──▶  명세서  ──▶  할 일 목록  ──▶  깃허브 이슈  ──▶  코드  ──▶  자동 검사
```

| 단계 | 답하는 질문 | 무엇이 더해지나 | 규모 |
|---|---|---|:-:|
| **기획서** | 무엇을 왜 만드나 | 기능 목록과 **타협하지 않을 기준** | 기능 15가지 |
| **명세서** | 그것을 **얼마나** 만족해야 하나 · **어떻게 확인**하나 | 항목마다 **출처 · 우선순위 · 확인 방법 · 담당자**를 붙임 | 기능 17 + 성능·안전 18 = **35개** |
| **할 일 목록** | **누가 어떤 순서로** 만드나 | 먼저 할 것 · 나중에 할 것 · 난이도 · 주차 | **68개** |
| **깃허브 이슈** | 지금 **어디까지** 왔나 | 조건별로 걸러 볼 수 있는 작업 카드 | **68개** |
| **코드** | 실제로 **도는가** | 화면 · 서버 · 데이터베이스 | — |
| **자동 검사** | **어겼는가** | 규칙을 어기면 **빌드를 세움** | — |

**단계마다 한 가지씩만 더합니다.** 기획서는 「왜」, 명세서는 「얼마나·어떻게 잴까」, 할 일 목록은 「순서」, 이슈는 「지금 어디」. 한 단계에서 두 가지를 하면 다음 단계가 무엇을 받았는지 알 수 없게 됩니다.

**발표 대본**

이걸 어떻게 관리했는지 한 장으로 보여드리겠습니다. 기획서에서 무엇을 왜 만드는지 정하고, 명세서에서 그걸 얼마나 만족해야 하는지와 어떻게 확인할지를 붙였습니다. 항목이 기능 열일곱 개, 성능과 안전 쪽이 열여덟 개 해서 서른다섯 개입니다. 그걸 개발 단위로 쪼개서 할 일 예순여덟 개를 만들고, 그대로 깃허브 이슈 예순여덟 개로 올렸습니다. 중요한 건 각 단계에서 한 가지씩만 더한다는 겁니다. 한 단계에서 두 가지를 하면 다음 단계가 무엇을 받았는지 알 수 없어집니다.

## B. 사슬이 끊기지 않았다는 증거

> **「다 이어져 있습니다」는 말이 아니라 숫자로 답합니다**

### 세 가지를 사람이 아니라 도구가 보증합니다

| 무엇 | 어떻게 |
|---|---|
| **할 일 문서** | 사람이 쓰지 않습니다. **원본 파일 하나**에서 자동으로 만들어집니다 |
| **「이게 밀리면 뭐가 밀리나」** | 먼저 할 일에서 **거꾸로 계산**합니다 — 손으로 적으면 반드시 어긋납니다 |
| **주차 배정** | 작업 순서도에서 **자동으로 뽑습니다** — 그래서 나중 것이 먼저 배치되는 일이 구조적으로 불가능합니다 |

### 점검 결과

| 항목 | 결과 |
|---|:-:|
| 번호 중복 | **0건** |
| 없는 작업을 먼저 하라고 적힌 것 | **0건** |
| 서로가 서로를 기다리는 순환 | **0건** |
| **근거 없이 만들어진 할 일** | **0건** |
| **완료 조건이 빠진 할 일** | **0건** |
| 주차 배정 누락 | **0건** |
| 순서 뒤집힘 | **0건** |

**빠진 요구사항 없음.** 명세서의 기능·성능·기술 항목 전부에 담당 작업이 붙어 있습니다.

### 넣지 않은 것도 이유를 남겼습니다

| 뺀 것 | 왜 |
|---|---|
| 다른 앱의 기록 가져오기 | 이번 범위 밖으로 확정 |
| 문자 대체 발송 | **아직 못 정한 것**에 걸림 — 외부 발송 업체가 정해지기 전까지 만들지 않음 |
| 위치 기반 알림 | **없애기로 한 기능** — 계획에 없음 |
| **AI 기능** | 🔴 **요구사항 35개 중 AI가 필요한 항목이 0개**였기 때문 |

> 🔴 **마지막 줄이 이 장의 결론입니다.** 저희는 AI를 넣을 자리를 찾다가 못 넣은 게 아니라, **요구사항에서 AI를 부르는 항목이 하나도 나오지 않아서** 안 넣었습니다.

**발표 대본**

이게 다 이어져 있다는 걸 말로만 하면 의미가 없어서, 세 가지를 사람이 아니라 도구가 보증하게 했습니다. 할 일 문서는 사람이 쓰지 않고 원본 파일 하나에서 자동으로 만들어집니다. 「이게 밀리면 뭐가 같이 밀리나」는 먼저 할 일에서 거꾸로 계산합니다. 주차 배정도 작업 순서도에서 자동으로 뽑아서, 나중에 할 일이 먼저 배치되는 게 구조적으로 불가능합니다. 점검해 보니 근거 없이 만들어진 할 일 0건, 완료 조건이 빠진 할 일 0건, 순환 0건입니다. 그리고 넣지 않은 것도 이유를 남겼는데, 그중 하나가 AI입니다. 요구사항 서른다섯 개 중에 AI가 필요한 항목이 하나도 없어서 안 넣었습니다. 자리를 찾다가 못 찾은 게 아니라 부르는 데가 없었던 겁니다.

## C. 하나를 끝까지 따라가기 — 별 이야기 *(백업)*

> **한 문장이 여섯 단계를 거쳐 코드가 됩니다**

### ① 기획서 — 무엇을 왜

> 아이가 모은 **별이 어긋나는 일은 0%** · **타협하지 않는다**
> *아이가 모은 것을 잃는 경험이라 「조금은 괜찮다」가 없다*

### ② 명세서 — 얼마나 · 어떻게 확인

한 줄이 **두 개**로 갈라집니다. **하나는 기능, 하나는 안전**입니다.

| | 요구사항 | 상세 | 확인 방법 |
|---|---|---|---|
| 기능 | 별을 주는 방법 — 여덟 가지 경우 · 쓰면 줄어듦 · 초기화 없음 | 여덟 경우의 증감을 장부에 남긴다. **현금으로 바꾸는 길이 코드에 아예 없어야** 한다 | 경우별 지급 시험 · **같은 요청 두 번 보내기 시험** · 장부 대조 · **현금 전환 코드 부재 자동 검사** |
| 안전 | 별 장부가 어긋나지 않을 것 | **오류율 0% — 타협 없음.** 되돌리는 장치를 두지 않는다. 1건이라도 어긋나면 **30분 내 확인** | 장부 대조 + 정산 결과 비교 |

🔴 **여기서 「확인 방법」 칸이 핵심입니다.** 요구사항을 적을 때 **어떻게 확인할지를 같이 적지 않으면**, 나중에 「했다」고 말할 근거가 없습니다.

### ③ 명세서의 지도 — 어디에 살 것인가

> 요구사항 → **담당 기능 묶음** → **부품** → **화면** → **시험 항목**
> 별 주기 → 별 장부 담당 → 장부 엔진 · 경우 분배기 · **중복 차단기** → 아이 홈 화면 → 시험 1건

### ④ 할 일 — 누가 어떤 순서로

> **별 장부 만들기** · 난이도 **상** · **2주차**
> 이것보다 **먼저 할 것 2개** / 이게 끝나야 시작되는 것 **11개**
> ⚠️ *이 하나가 밀리면 열한 개가 함께 밀린다*

### ⑤ 깃허브 이슈 — 지금 어디까지

> 이슈 한 건에 **꼬리표 여섯 개**
> 어느 영역인지 · 난이도 · 작업 성격 · 몇 주차인지 · 개발인지 디자인인지

**꼬리표를 여섯 축으로 붙인 이유** — 「이번 주차에 내가 할 개발 쪽 어려운 작업」이 **한 번 걸러서** 나와야 하기 때문입니다.

### ⑥ 코드 — 실제로 도는 것

> **잔액을 저장하지 않습니다.** 장부에 쌓인 것의 합이 곧 잔액입니다
> 중복 지급은 코드가 판단하지 않고 **데이터베이스가 거부**합니다
> 합이 어긋난 줄은 **표시만** 하고 아이 별은 건드리지 않습니다

**발표 대본**

하나만 끝까지 따라가 보겠습니다. 기획서에 「아이가 모은 별이 어긋나는 일은 0퍼센트, 타협하지 않는다」라고 한 줄 있습니다. 아이가 모은 걸 잃는 경험이라 「조금은 괜찮다」를 안 두기로 한 겁니다. 이게 명세서에서 두 개로 갈라집니다. 하나는 기능, 하나는 안전입니다. 여기서 중요한 게 확인 방법 칸인데, 요구사항을 적을 때 어떻게 확인할지를 같이 적었습니다. 이걸 안 적으면 나중에 「했다」고 말할 근거가 없습니다. 그다음 명세서 안에 지도가 있어서, 이 요구사항이 어느 기능 묶음, 어느 부품, 어느 화면, 어느 시험에 사는지를 지정합니다. 그게 할 일 하나가 되는데, 난이도 상, 2주차, 이게 끝나야 시작되는 게 열한 개라고 적혀 있습니다. 그대로 깃허브 이슈가 됐고 꼬리표가 여섯 개 붙어 있습니다. 그리고 실제 코드에서는 잔액을 아예 저장하지 않고, 중복은 데이터베이스가 거부합니다.

## D. 기능 · 성능 · 상태 · 예외가 어디서 붙나 *(백업)*

> **작업 카드의 칸 네 개가 각각 하나씩 담당합니다**

이슈 본문은 자유롭게 쓰는 게 아니라 **정해진 서식**입니다. 그래서 무엇이 빠졌는지 눈으로 셀 수 있습니다.

| 축 | 어느 칸에 | 형태 | 예 |
|---|---|---|---|
| **기능** | **실행 계획** | 할 일 체크 목록 | *여덟 가지 경우에 별 주기* |
| **상태** | **실행 계획** | **상태가 어떻게 바뀌는지**를 한 줄로 | *완료 → 대기 → 승인 / 거절* |
| **성능 · 안전** | **지켜야 할 조건** | 안정성 · 속도 · 규제 세 줄 | *어긋남 0% · 별 반영 0.8초 안 · 별은 모으기만* |
| **예외** | **완료 조건**의 **실패 경우** | 「이런 상태에서 이렇게 하면 이렇게 된다」 | *현금으로 바꾸는 코드가 들어오면 → **빌드가 실패한다*** |
| **끝났다는 판정** | **완료 판정** | 체크 목록 | *같은 요청 두 번 보내도 중복 0건임을 증명했는가* |
| **일정 영향** | **선행 · 후행** | 먼저 / 나중 | *이게 끝나야 시작되는 것 11개* |

### 상태와 예외를 왜 따로 적는가

**미션 승인**이 좋은 예입니다.

- **상태** — 완료 → **대기** → 승인 / **거절**. 네 가지를 다 적지 않으면 「거절」이 만들 때 사라집니다.
- **예외** — 그래서 완료 조건에 *"거절이 **안 한 것과 다르게 보이는가**"* 를 따로 겁니다.
- **이유** — 거절이 안 한 것과 같아 보이면 **아이 화면이 거짓말**을 합니다. 아이는 했는데 안 한 것으로 보입니다.

🔴 **저희에게 예외는 「오류 처리」가 아니라 「사용자가 겪는 나쁜 경우」입니다.** 그래서 기능 옆이 아니라 **완료 조건 안에** 넣었습니다 — 통과 여부를 재야 하기 때문입니다.

**발표 대본**

작업 카드는 자유롭게 쓰는 게 아니라 정해진 서식입니다. 칸이 여섯 개인데, 기능이랑 상태는 실행 계획에, 성능이랑 안전은 조건 칸에, 예외는 완료 조건의 실패 경우에 들어갑니다. 서식이 정해져 있어서 무엇이 빠졌는지 눈으로 셀 수 있습니다. 상태랑 예외를 왜 따로 적었냐면, 미션 승인이 좋은 예입니다. 완료, 대기, 승인, 거절 네 가지가 있는데 이걸 다 안 적으면 만들 때 「거절」이 사라집니다. 그리고 거절이 안 한 것과 같아 보이면 아이 화면이 거짓말을 합니다. 아이는 했는데 안 한 걸로 보이는 거죠. 그래서 「거절이 안 한 것과 다르게 보이는가」를 완료 조건으로 따로 걸었습니다. 저희한테 예외는 오류 처리가 아니라 사용자가 겪는 나쁜 경우입니다.

## 예상 질문과 답

**Q. 이슈를 68개나 손으로 만드셨나요?**
아니요. 할 일 문서와 이슈 **둘 다 원본 파일 하나에서 자동으로 만들어집니다.** 이슈를 만들면 할 일과 이슈 번호가 자동으로 짝지어지고, 본문에서 서로를 가리키는 부분이 실제 번호로 바뀝니다. 손으로 만들면 예순여덟 개 중 몇 개는 반드시 어긋납니다.

**Q. 요구사항이 바뀌면 어떻게 하나요?**
원본 파일을 고치고 문서를 다시 만듭니다. 할 일 문서를 직접 고치지 말라고 문서 첫머리에 적어 뒀습니다 — 「이게 밀리면 뭐가 밀리나」가 자동 계산이라 손으로 고치면 어긋납니다.

**Q. 빠뜨린 요구사항이 없다는 건 어떻게 아나요?**
양쪽에서 셉니다. 요구사항 쪽에서는 **담당 작업이 없는 항목이 0개**, 작업 쪽에서는 **근거 요구사항이 없는 작업이 0개**입니다. 한쪽만 보면 늘어난 걸 못 잡습니다.

**Q. 문서대로 정확히 만들어졌나요?**
아니요. **달라진 곳이 있고 그것도 기록해 뒀습니다.** 개발하면서 문서와 달라진 지점마다 번호를 붙여 따로 장부에 남겼습니다 — 무엇이 왜 달라졌는지, 되돌릴지 문서를 고칠지까지 적혀 있습니다. 예를 들어 부모와 아이 화면을 서로 다른 주소로 나누려던 것은 하나의 앱이라 못 나눴고, 대신 세 겹으로 막으면서 그 대가를 장부에 적었습니다.
